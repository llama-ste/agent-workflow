# 작업 기록과 의사결정 로그

한 작업의 **의사결정 서사**를 남긴다. 느낀 점 회고가 아니라, "무슨 문제로 시작 → 어떤 방향들이 있었나 → 트레이드오프를 어떻게 저울질해 무엇을 결정 → 결과"를 기록한다.
연말 성과 정리와 포트폴리오에서 판단 근거를 그대로 꺼내 쓰는 것이 목적이다.

## 언제 남기나

- 사용자가 "작업 기록 남겨줘", "worklog 남겨줘" 등으로 요청하면 실행한다.
- 의미 있는 작업을 마쳤거나 PR·인계 등 자연스러운 종료 지점에서는 기록을 남길지 **한 번 가볍게 제안**할 수 있다. 제안은 실행이 아니며, 사용자가 동의할 때만 기록한다.
- 자동으로 기록하지 않는다. 요청이나 동의가 없으면 기록하지 않고, 같은 작업에 반복해서 다시 권하지 않는다.
- 기록은 별도 구현·커밋·전송을 유발하지 않는다. 기본 결과는 로컬 파일 생성까지다.

## 무엇을 기록하나

먼저 이번 작업의 실제 내용을 확인한다. 대화의 목표·변경·검증 결과와 Git 상태(브랜치, `git status --short`, 관련 diff, PR·커밋 링크)를 근거로 삼는다.
확정 사실과 추정을 구분하고, 근거 없는 판단 서사를 지어내지 않는다.

## 기록 형식

작업 중인 저장소의 기록 위치(`journal/<연도>/<날짜>-<슬러그>.md` 또는 프로젝트 문서 관례)에 저장한다. 예: `journal/2026/2026-09-17-discount-calc-decision.md`.
같은 경로가 이미 있으면 덮어쓰지 않고 슬러그를 조정한다.

```markdown
---
date: 2026-09-17
project: <저장소/제품 이름>
title: <한 줄 제목>
type: feature            # feature | bugfix | refactor | decision | ops | review
scope: <도메인 예: 결제/할인>
decision: <한 줄 결론 — 연말·포트폴리오 스캔용>
outcome: 완료             # 완료 | 진행중 | 보류
links: [PR/이슈/커밋 URL]
---

## 배경 — 무슨 문제로 시작했나
## 검토한 방향 — 어떤 선택지가 있었나
## 트레이드오프와 결정 — 무엇을 왜 골랐나
## 결과 — 실제로 어떻게 됐나
## 남은 것 (선택)
```

- 프론트매터는 나중에 집계·검색·외부 서비스 속성 매핑에 쓰인다. 필드를 임의로 늘리지 말고 필요하면 먼저 제안한다.
- 본문의 핵심은 "트레이드오프와 결정" 섹션이다. 고른 선택지뿐 아니라 **버린 선택지와 이유**를 함께 남긴다.
- 민감한 값(키·토큰·인증 정보·개인정보)은 기록하지 않는다. 필요하면 위치와 변수 이름만 남긴다.

## 이미지와 시각 자료

글만 있는 기록은 나중에 다시 읽히지 않는다. 판단과 결과를 빠르게 보여주는 시각 자료를 함께 남긴다.

- 화면 변화는 전/후 스크린샷, 구조·흐름은 다이어그램, 수치는 그래프로 남긴다.
- 이미지 파일은 기록과 같은 위치의 `assets/<슬러그>/`에 두고, 본문에서 `![설명](assets/<슬러그>/파일)`로 참조한다.
- 민감 정보(내부 URL·개인정보·키)가 담긴 화면은 가리거나 제외한다.
- 이 마크다운 원본은 Notion·블로그·HTML 등에서 이미지와 서식이 그대로 보기 좋게 렌더링된다. 캡처 단계의 목적은 표현 재료(스크린샷·다이어그램·결론 한 줄)를 잘 남기는 것이다.

## 중앙 보관과 전달 (선택)

작업 저장소의 로컬 기록이 기본 원본이다. 이를 개인 중앙 저장소(Notion 등)로 모아 성과 정리·회고·글쓰기에 활용한다.
외부 서비스 전송은 도구별 연결 계층에서 다루며, 같은 프론트매터를 서비스 속성으로 매핑한다. 연결이 없어도 로컬 기록은 그대로 동작한다.
사적인 기록은 공개 저장소에 커밋하지 않는다. 공개 대상 저장소에서는 기록 위치를 버전 관리에서 제외하거나 중앙 저장소로만 보관한다.
