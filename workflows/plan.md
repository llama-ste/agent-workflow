# 요구사항에서 실행 가능한 작업까지

새 기능·새 도메인·여러 영역의 리팩토링 또는 요구사항이 불명확한 작업에 적용한다.
흐름은 요구사항 구체화 → 스펙 → 작업 분해 → 구현 → 검증·리뷰다.
작은 수정은 대화의 목표와 검증 기준으로 충분하며 별도 문서·티켓을 강제하지 않는다.
이미 확정된 단계는 재작성하지 않고 해당 자료를 읽고 다음 단계로 진행한다.

## 1. 요구사항 구체화

기존 코드가 있으면 `guides/impact-scope.md`에 따라 현재 동작과 도메인 문서를 먼저 조사한다.
신규 작업이면 사용자·해결할 문제·운영 환경부터 확인한다.

- 사용자가 달성할 결과와 현재 문제는 무엇인가?
- 정상 동작과 실패·경계 조건은 무엇인가?
- 반드시 지킬 호환성·보안·성능·일정 제약은 무엇인가?
- 이번에 하지 않을 일과 후속 작업은 무엇인가?
- 구현 방향을 바꿀 미결정 사항은 무엇인가?

질문은 조사로 답할 수 없는 결정에 집중한다. 한 번에 부담을 주는 질문 목록이나 끝없는 인터뷰를 만들지 않는다.
새 도메인의 용어가 모호하면 주요 개념과 관계를 정리한다. 확정 사실과 가정을 구분한다.

대화형 입력(슬랙 스레드·회의 메모 등)은 결정된 사항 / 논의 중 / 모순·미결로 분류한다. 스레드 안의 번복이나 상충하는 지점은 임의로 고르지 않고 짚어 확인한다.

### 이해 확인

정리가 끝나면 다음 단계로 넘어가기 전에 이해가 맞는지 확인받는다. 이 단계를 건너뛰고 스펙 작성으로 넘어가지 않는다.

- 이해한 목표·범위·비목표를 한 문단으로 재진술한다.
- 방향을 바꿀 핵심 결정 2~4개를 **확인 퀴즈**로 제시한다. 예: "이번 범위에 X가 포함됩니까, 후속입니까?", "Y가 실패하면 기대 동작은 A입니까 B입니까?" 사용자의 답이 어긋난 이해를 드러낸다.
- 퀴즈는 결과·범위를 가르는 항목에만 쓴다. 이미 명확한 것을 형식적으로 묻지 않고, 퀴즈로 인터뷰를 늘리지 않는다.
- 작은 작업은 한 문단 재진술로 충분하며 퀴즈를 생략할 수 있다.

**산출물:** 문제, 목표, 비목표, 제약, 주요 용어, 미결정 질문, 확인된 이해(재진술 + 퀴즈 응답).
**완료 조건:** 사용자가 원하는 결과를 검증 가능한 문장으로 설명할 수 있고, 재진술과 확인 퀴즈로 이해 일치가 확인되었으며, 방향을 바꾸는 질문이 해결되어 있다.

## 2. 스펙 작성

대화나 기존 프로젝트 문서 위치에 다음을 정리한다. 큰 기능·장기 작업은 후속 세션에서도 읽을 수 있는 문서로 남긴다.

```text
문제와 목표
범위와 비목표
사용자 시나리오와 입력·출력
실패·경계 조건 및 수용 기준
데이터·API·호환성 영향
검증 방법과 필요 시 배포·복구 조건
미결정 사항
```

구현 세부사항을 요구사항처럼 고정하지 않는다. 중요한 설계 결정은 근거와 대안을 구분해 남긴다.
새 모듈·경계 설계가 필요하면 `guides/design-discipline.md`를 함께 사용한다.
명확하지 않은 결정은 질문하고, 이미 합의된 내용을 형식적으로 다시 승인받지는 않는다.

**산출물:** 요구사항별로 확인 방법이 연결된 스펙.
**완료 조건:** 필수 동작과 비목표를 구분할 수 있고 구현 후 충족 여부를 판단할 수 있다.

## 3. 작업 분해

- 작업은 파일별 기계적 분할보다 검증 가능한 동작 단위로 나눈다.
- 각 작업에 목적, 범위, 선행 조건, 관련 스펙, 완료 기준, 검증 방법을 기록한다.
- 데이터 변경·호환성 작업의 순서를 드러낸다. 임시 상태가 안전한지도 확인한다.
- 각 작업만 통과해도 통합 동작이 빠질 수 있으므로 마지막 통합 검증을 포함한다.
- 사용자 요청이나 프로젝트 관례가 없다면 외부 이슈를 발행하지 않는다. 로컬 목록으로 충분하다.

**산출물:** 실행 순서와 의존성이 있는 작업 목록.
**완료 조건:** 다음 작업의 시작 조건과 완료 조건이 명확하고, 스펙의 필수 항목이 작업 목록에 대응한다.

## 4. 구현과 피드백

`workflows/implement.md`에 따라 한 작업씩 구현·검증한다. 버그는 실패 재현, 기능은 요구한 동작을 검증하는 테스트를 기준으로 진행한다.
새 사실이 스펙을 바꾸면 영향과 이유를 설명하고 문서·작업 목록을 함께 갱신한다.
요구사항 누락과 코드 품질을 각각 검토하고, 큰 변경의 최종 점검에는 `workflows/review.md`의 기준을 사용한다.
완료 시 스펙 충족·검증 결과·남은 문제를 보고한다. 구현 완료만으로 커밋·공개·배포를 수행하지 않는다.

외부 스킬은 이 절차를 돕는 선택 수단이다. 특정 명령이나 플러그인이 없어도 동일한 산출물을 만들 수 있어야 한다.
