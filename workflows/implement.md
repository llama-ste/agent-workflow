# 구현 절차

기능 추가, 버그 수정, 리팩토링에 적용한다. 작업 규모에 맞게 수행하되 조사·검증을 생략했다면 이유를 밝힌다.

## 1. 목표와 현재 상태 확인

- 요청을 관찰 가능한 성공 기준으로 바꾼다. 무엇을 바꾸고 어디까지 검증할지 밝힌다.
- 프로젝트 지침, 관련 README·설계 결정·도메인 문서를 읽는다. 없는 문서를 형식적으로 만들지는 않는다.
- Git 저장소라면 브랜치와 staged·unstaged·untracked 상태를 확인해 기존 사용자 변경을 파악한다.
- 테스트·타입 검사·빌드 명령을 프로젝트 설정과 CI에서 확인한다. 특정 패키지 관리자나 기본 브랜치를 추측하지 않는다.
- 결과·공개 인터페이스·데이터 처리 방식이 달라지는 모호함은 구현 전에 질문한다. 사소한 선택은 기존 관례를 따른다.

## 2. 영향 범위 조사

`guides/impact-scope.md`를 읽고 도메인·호출부·호환성·중복 구현·의존성을 조사한다.
새 모듈이나 공개 경계를 설계한다면 `guides/design-discipline.md`를 함께 읽는다.
이 저장소 밖에서는 생성 지침의 절대 경로 목록으로 문서를 찾는다.

## 3. 작업에 맞는 계획

| 작업 | 진행 방식 | 성공 기준 예시 |
| --- | --- | --- |
| 작은 수정 | 짧게 의도를 밝히고 바로 수정·검증 | 지정한 문구나 동작만 변경 |
| 버그 수정 | 재현 → 최소 수정 → 회귀 검증 | 수정 전 실패하던 시나리오가 통과 |
| 기능 추가 | 계약·경계값 확인 → 구현 → 관련 검증 | 요구한 정상·실패 동작을 확인 |
| 리팩토링 | 기존 동작 확인 → 구조 변경 → 동일 검증 | 관찰 가능한 동작과 계약 유지 |
| 큰 기능 | 요구사항·비목표 정리 → 검증 가능한 작업 단위로 분해 | 단계별 결과와 통합 동작 확인 |

큰 작업의 기록은 기존 프로젝트 문서 위치를 따른다. 외부 스킬, 이슈 트래커, 특정 설계 방식은 필수 조건이 아니다.
각 단계에는 수행할 일과 확인 방법을 포함한다. 이미 승인된 범위 안에서 단계마다 승인을 요구하지 않는다.
요구사항 구체화·스펙·작업 분해가 필요하면 `workflows/plan.md`의 산출물과 완료 조건을 따른다.

## 4. 구현과 검증

- 버그는 가능한 한 수정 전에 재현한다. 재현하지 못하면 확인한 사실과 가설을 구분한다.
- 한 번에 검증할 수 있는 크기로 변경한다. 기존 스타일과 공개 계약을 유지하며 필요한 부분만 수정한다.
- 동작 변경에는 관련 테스트를 추가·갱신한다. 버그 테스트는 원래 오류를 실제로 검출하는지 확인한다.
- 경계값과 실패 경로는 변경된 동작에 맞게 선택한다. 내부 구현을 그대로 복제한 테스트를 만들지 않는다.
- 가장 관련된 검증부터 실행하고 프로젝트 필수 검증을 수행한다. 결과에 따라 추가 검증 범위를 정한다.
- 실패하면 자신의 변경이 만든 실패인지 기존 실패·환경 문제인지 조사한다. 통과시키기 위해 무관한 테스트를 삭제하거나 약화하지 않는다.
- 접근법이 작동하지 않으면 원인을 정리하고 계획을 수정한다. 무관한 파일까지 수정하며 같은 시도를 반복하지 않는다.

## 5. 완료 전 확인과 보고

- diff와 새 파일을 확인해 요구사항 누락, 요청 범위 밖 변경, 비밀값, 임시 디버깅 코드가 없는지 검토한다.
- 사용자의 기존 변경을 보존했는지 확인한다. 자신의 변경으로 불필요해진 코드만 정리한다.
- 큰 변경은 `workflows/review.md` 기준으로 자체 점검한다. 별도 리뷰를 수행한 것처럼 표현하지 않고 실제 점검 범위를 밝힌다.
- 테스트 통과와 요구사항 충족을 별개로 확인한다. 테스트가 통과해도 요청한 동작이 빠졌다면 완료가 아니다.
- 완료 보고에는 핵심 변경과 이유, 실행한 검증과 결과, 미실행 검증과 사유, 남은 문제를 포함한다.
- 진행이 막혔다면 완료한 범위와 다음 진행에 필요한 조건을 명확히 보고한다. 미완료 작업을 완료로 표현하지 않는다.
- 커밋·푸시·배포는 요청 범위에 포함되었을 때만 진행한다.
