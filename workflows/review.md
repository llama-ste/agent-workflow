# 코드 리뷰 절차

사용자가 코드 리뷰를 요청한 경우에 적용한다. 단순히 문장에 '리뷰'가 있다는 이유로 전환하지 않는다.

## 1. 대상과 비교 기준 확정

- 프로젝트 지침과 현재 작업 상태를 확인한다. 사용자가 지정한 파일·변경·커밋·PR을 우선한다.
- 작업 중 변경을 검토한다면 staged, unstaged, untracked 중 무엇을 포함하는지 명시한다. 미추적 파일은 일반 diff에 나타나지 않는다.
- 브랜치나 PR을 검토한다면 대상과 기준 ref를 기록한다. 기능 브랜치의 변경은 보통 merge-base와 대상 HEAD 사이를 비교하며, 사용자가 두 시점의 직접 비교를 요청했다면 그 기준을 따른다.
- 기본 브랜치 이름을 추측하지 않는다. 저장소 정보로 기준을 확인하고, 범위를 결정할 수 없을 때 질문한다.
- 기존 결함과 이번 변경이 새로 만들거나 악화한 결함을 구분한다. 특정 파일 전체 리뷰라면 기존 결함도 대상에 포함한다.
- 요구사항·이슈·설계 문서가 있으면 읽는다. 없으면 코드에서 확인한 계약과 가정을 밝히고, 존재하지 않는 요구사항을 만들어내지 않는다.

## 2. 변경의 동작 이해

1. 변경 요지를 파악하고 입력 → 처리 → 출력·부수효과의 흐름을 따라간다.
2. diff 주변 구현, 호출부, 공유 타입, 설정, 관련 테스트를 확인한다. 변경된 줄만 보고 결론내리지 않는다.
3. 이전 동작과 비교해 어떤 사용자·호출자·데이터가 영향을 받는지 확인한다.
4. 결함 후보마다 실제 도달 가능한 입력이나 실행 순서를 구성한다. 기존 검증·상위 계층·프레임워크가 이미 방지하는지 확인한다.
5. 필요하면 최소 재현이나 관련 테스트로 확인한다. 코드로 확인한 사실과 실행으로 재현한 사실을 구분한다.

## 3. 검토 기준

아래 항목을 변경의 성격에 맞게 검토한다. 무관한 항목에 대해 형식적인 보고를 만들지 않는다.

| 관점 | 확인할 질문 |
| --- | --- |
| 요구사항 | 필수 동작이 누락되거나 반대로 구현되었는가? 요청하지 않은 동작이 추가되었는가? |
| 정확성·경계값 | 빈 값, 누락, 0, 최솟값·최댓값, 중복, 정렬, 시간대, 반올림에서 계약을 지키는가? |
| 영향 범위 | 호출자와 공유 상태에 어떤 변화가 생기는가? 성공·실패 경로 모두 기존 불변식을 지키는가? |
| 계약·호환성 | API, 타입, 저장 형식, 설정 기본값 변경이 기존 소비자를 깨뜨리는가? |
| 데이터 정합성 | 부분 저장, 중복 실행, 트랜잭션 경계, 마이그레이션과 구버전 공존을 처리하는가? |
| 동시성 | 경쟁 조건, 비동기 순서, 잠금, 취소, 재시도로 결과가 달라지거나 부수효과가 중복되는가? |
| 실패·복구 | 오류가 누락되거나 성공으로 표시되는가? 타임아웃, 재시도 한계, 자원 해제가 적절한가? |
| 보안·정보 보호 | 입력 신뢰 경계, 인증·인가, 주입, 경로 접근, 비밀값·개인정보 노출에 문제가 있는가? |
| 성능 | 실제 데이터 규모에서 반복 쿼리, 무제한 조회, 불필요한 연산·메모리 사용이 문제가 되는가? |
| 운영·관측 | 설정·배포 순서·롤백 조건이 맞는가? 장애를 구분할 정보가 남고 민감한 값은 숨기는가? |
| 테스트 | 바뀐 계약과 실패 경로를 검증하는가? 버그가 있는 구현도 통과하는 테스트는 아닌가? |

언어·프레임워크별 동작이 결론을 좌우하면 저장소에 설치된 버전과 공식 문서·구현으로 확인한다.
설계나 스타일 차이는 구체적인 결함 또는 프로젝트 규칙 위반으로 이어질 때 지적한다.
취향, 추측성 성능 문제, 무관한 현대화 제안을 결함처럼 보고하지 않는다.

### 코드베이스 일관성과 설계

- 같은 계층·주변 구현의 명명, 오류 처리, 의존성 방향과 비교한다.
- 새 모듈·공개 경계가 포함되면 `guides/design-discipline.md` 기준으로 책임과 테스트 경계를 확인한다.
- 기존 관례와 다른 선택에는 이유가 있는지 확인한다. 일관성만을 위해 결함 있는 패턴을 확대하도록 요구하지 않는다.
- 공식적으로 폐기된 API나 근거 있는 보안·성능·정합성 문제는 사실·영향·대안을 보고한다. 무관한 현대화는 별도 참고 사항으로 구분한다.

### 스펙 충실도

요구사항 문서가 있으면 코드 품질과 별도로 `누락 / 범위 초과 / 오구현`을 확인한다.
각 발견에 해당 요구사항 위치를 연결한다. 결함이 없다는 판단이 요구사항 충족을 대신하지 않는다.
스펙이 없다면 제공된 요청과 확인 가능한 계약을 기준으로 삼고 그 한계를 밝힌다.

## 4. 발견 사항의 근거와 우선순위

보고 전 각 후보를 확인한다:

- 발생 조건이 실제로 가능한가?
- 어느 위치에서 어떤 계약이 깨지며, 사용자나 시스템에 어떤 영향이 있는가?
- 호출부나 다른 계층에서 이미 처리하고 있지는 않은가?
- 별개 항목처럼 보이는 발견이 같은 원인에서 비롯된 것은 아닌가?

심각도는 영향과 발생 가능성으로 판단한다:

| 심각도 | 기준 |
| --- | --- |
| 차단 | 주요 기능 사용 불가, 데이터 손실, 권한 우회 등으로 반영 전에 반드시 해결해야 함 |
| 중요 | 현실적인 조건에서 오동작·회귀·호환성 문제가 발생해 반영 전 수정이 필요함 |
| 경미 | 영향이 제한적이지만 근거가 명확한 결함. 후속 수정 여부를 판단할 수 있음 |

심각도와 확신도는 별개다. 근거는 `실행 재현`, `코드로 확인`, `조건부 추정`으로 구분한다.
조건부 추정에는 성립 조건과 미확인 사항을 쓴다. 영향 자체를 입증할 수 없는 후보는 확정 결함으로 올리지 않고 필요한 질문으로 남긴다.
발견 개수를 맞추기 위해 항목을 만들지 않는다.

## 5. 결과 보고

### 전달 방식

- 결과는 먼저 채팅에서 읽을 수 있는 완결된 보고서로 제공한다. 요약만 쓰고 상세 내용을 파일로만 넘기지 않는다.
- 요약을 맨 앞에 두고, 제목으로 각 섹션을 구분한다. 발견 사항은 `차단 → 중요 → 경미` 순서로 묶는다.
- 같은 중요도 안에서는 영향 범위와 발생 가능성이 큰 항목을 먼저 둔다. 검토 카테고리별로 재분류해 우선순위를 흐리지 않는다.
- 사용자가 파일을 요청하면 보고서를 파일로도 제공한다. 최초 요청에 파일 저장이 포함되어 있으면 추가 확인 없이 채팅 보고와 저장을 함께 수행한다.
- 프로젝트나 사용자가 지정한 보고 형식이 있으면 우선한다.

### 채팅 보고 형식

아래 구조를 사용한다. 대괄호는 실제 내용으로 채우고, 발견이 없는 중요도 섹션은 생략한다.
발견 번호는 보고서 전체에서 연속으로 부여해 후속 논의에서 항목을 지정할 수 있게 한다.

````markdown
## 리뷰 요약

- 판단: [반영 전 수정 필요 / 추가 확인 필요 / 검토 범위에서 보고할 결함을 찾지 못함]
- 발견: 차단 [N]건 · 중요 [N]건 · 경미 [N]건
- 핵심: [가장 중요한 문제와 영향, 최대 3개]
- 우선 조치: [먼저 해결하거나 확인할 일]

## 검토 범위

- 대상·비교 기준: [파일, 변경 범위, 기준 ref와 대상 ref 등]
- 변경 요지: [이번 변경이 바꾸는 동작]

## 차단

### 1. [문제를 구체적으로 설명하는 제목]

- 위치: [파일 링크와 최소한의 관련 줄]
- 조건과 영향: [어떤 입력·순서에서 무엇이 잘못되는지]
- 근거: [실행 재현 / 코드로 확인 / 조건부 추정] [구현·호출부·요구사항 또는 재현 결과]
- 수정 방향: [문제를 해결하는 데 필요한 최소 방향]

## 중요

### 2. [문제를 구체적으로 설명하는 제목]

[위와 동일한 항목]

## 경미

### 3. [문제를 구체적으로 설명하는 제목]

[위와 동일한 항목]

## 요구사항 충족 여부

[스펙이나 명확한 요구사항이 있을 때 충족·누락·범위 초과·오구현을 요약]
[이미 보고한 발견은 번호로 참조하고 중복 집계하지 않음]

## 검증과 한계

- 실행한 검증: [명령과 결과 또는 실행하지 않음]
- 미확인 범위: [미실행 검증, 환경 제약과 사유]
- 남은 질문: [판단에 필요한 미확인 조건]
````

- 요약은 상세 발견과 건수·판단이 일치해야 한다. 반영을 막는 발견이 있으면 명확히 밝힌다.
- 미확인 조건이 결론을 좌우하면 '추가 확인 필요'로 표시한다. 조건부 추정은 요약에서도 확정 사실처럼 표현하지 않는다.
- 경미한 발견만 있으면 판단을 '경미한 수정 권장'으로 적을 수 있다. 무조건적인 반영 가능 판정을 내리지 않는다.
- 발견이 없으면 요약·검토 범위·검증과 한계를 남긴다. 빈 발견 섹션과 불필요한 우선 조치는 생략하고, 결함이 없다고 보장하지 않는다.
- 요구사항 문서가 없는 경우 해당 섹션은 생략하고 검토 범위에 판단 근거를 적는다.
- 결함으로 확정하지 않은 질문이나 참고 제안은 발견 건수에 포함하지 않는다. 필요한 참고 사항은 별도 섹션에 둔다.
- 수정 방향을 제시하기 위해 전체 구현을 다시 작성하지 않는다.

### 파일로 제공할 때

- 기본 형식은 Markdown이며 사용자가 지정한 형식과 경로를 우선한다. 지정이 없으면 프로젝트 문서 관례에 맞는 새 경로를 선택한다.
- 채팅의 요약·발견·근거·검증 한계를 동일하게 보존하고 리뷰 시점과 대상 ref 또는 작업 상태를 기록한다.
- 후속 저장 요청만으로 재리뷰하거나 발견 내용을 바꾸지 않는다. 코드가 바뀌었다면 이전 시점의 리뷰를 저장한 것임을 밝힌다.
- 기존 파일을 임의로 덮어쓰지 않는다. 저장 후 실제 파일 경로를 채팅에 링크한다.
- 파일 제공을 원하는지 매번 질문하지 않는다. 별도 요청이 없으면 채팅 보고로 완료한다.

## 6. 작업 상태 보존

- 리뷰만 요청받았다면 소스 수정, 커밋, 브랜치 전환, pull을 수행하지 않는다.
- 테스트가 파일 생성·데이터 변경·외부 호출을 하는지 먼저 확인한다. 격리가 필요한 경우에만 별도 작업 사본을 사용한다.
- 리뷰 중 사용자 변경을 되돌리지 않는다. 생성물이 생기면 자신이 만든 것인지 확인하고 처리 내역을 알린다.
- 결과는 기본적으로 대화에 보고한다. 파일 저장이나 수정 작업으로의 전환은 요청받았을 때 수행한다.
