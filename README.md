# 개인 AI 워크플로우

AI 코딩 에이전트와의 작업을 **계획 · 구현 · 검증 · 리뷰 · 기록**의 절차로 고정한 개인 운영 체계다.
절차와 규칙을 도구·모델에 종속되지 않는 단일 원본으로 관리하고, 어느 환경에서든 전역으로 연결해 동일하게 적용한다.

## 왜 만들었나

AI 에이전트와의 작업은 매번 즉흥적으로 흐른다. 같은 종류의 일(기능 추가, 버그 수정, 리뷰, 인계)인데도 세션마다 조사 범위가 다르고, 무엇을 검증했는지가 일정하지 않고, 완료 기준이 그때그때 달라진다. 도구(Codex·Claude Code)를 바꾸면 같은 지시를 처음부터 다시 해야 한다.

그래서 **각 단계에서 무엇을 확인하고 어떻게 완료를 판단할지를 절차로 고정**했다. 요구사항을 세우는 방법, 영향 범위를 조사하는 기준, 검증과 완료 보고의 형식, 리뷰의 심각도 판단까지 문서로 정의하고, 이를 단일 원본으로 관리해 환경과 무관하게 적용한다.

## 작업 절차

작업 성격에 맞는 절차만 읽어 적용한다. 각 절차는 확인 항목과 완료 기준을 정의한다.
검증은 두 시점으로 나뉜다. **무엇이 통과하면 완료인지(성공 기준)는 구현 전에 정하고, 실제 검증 실행은 구현 후에** 한다.

**계획 수립** ([plan.md](workflows/plan.md)) — 모호한 요청을 **합의된 실행 계획**으로 바꾸는 단계다. 문제·목표·비목표와 제약을 세우고, 조사로 답할 수 없는 결정만 질문한다. 이해한 내용을 재진술하고 **확인 퀴즈로 합의를 확인한 뒤** 스펙과 작업 단위로 분해한다. 어긋난 방향으로 구현이 쌓이는 것을 초입에서 막는다.

**구현** ([implement.md](workflows/implement.md)) — 요청을 검증 가능한 성공 기준으로 바꾸고, 도메인·호출부·호환성 영향을 조사한 뒤([impact-scope.md](guides/impact-scope.md)) 구현한다. 버그는 실패를 재현한 다음 수정한다. 새 경계를 설계할 때는 책임과 테스트 경계를 따진다([design-discipline.md](guides/design-discipline.md)).

**검증과 완료 보고** — 변경과 관련된 검증을 실행하고, 실행한 것과 하지 않은 것을 구분해 보고한다. 요구사항 충족과 검증 통과를 각각 확인하며, 미검증을 완료로 표현하지 않는다.

**리뷰** ([review.md](workflows/review.md)) — 대상과 비교 기준을 확정하고, 결함 후보가 실제로 도달 가능한 조건인지 확인한다. 심각도(차단·중요·경미)와 근거 수준(실행 재현·코드 확인·조건부 추정)을 구분해 보고한다.

**인계와 기록** ([handoff.md](workflows/handoff.md), [worklog.md](workflows/worklog.md)) — 세션이나 모델이 바뀌면 재개에 필요한 상태를 파일로 넘기고, 작업이 끝나면 의사결정 서사를 기록으로 남긴다.

## 공통 규칙

절차와 별도로, 모든 작업에 적용되는 기본값이다. 각 항목은 에이전트가 자주 벗어나는 지점을 겨냥한다.

- **구현 전 사고** — 가정·성공 기준을 먼저 밝히고, 해석이 갈리면 임의로 고르지 않고 질문한다.
- **단순함** — 문제를 해결하는 최소한의 코드만 쓴다. 요청하지 않은 기능·설정·추상화를 더하지 않는다.
- **최소 변경** — 요청과 직접 연결된 것만 건드린다. 주변 코드를 임의로 "개선"하거나 미커밋 변경을 덮지 않는다.
- **검증 기반 완료** — 실행하지 않은 검증을 통과했다고 말하지 않는다.
- **위험 작업 게이팅** — 강제 푸시, 대량 삭제, 배포처럼 되돌리기 어려운 작업은 권한을 확인하고 멈춘다.
- **자율성의 경계** — 승인된 범위는 자율로 진행하되, 범위 자체를 바꾸는 선택은 확인받는다.

위는 발췌다. 응답 언어·정보 보호·산출물 위치를 포함한 전체 규칙은 [AGENTS.md](AGENTS.md)에 있다.

## 핵심 설계 결정

**도구 중립 원본 + 도구별 어댑터.** 규칙·절차(`AGENTS.md`, `workflows/`, `guides/`)는 특정 도구를 가정하지 않는다. 도구마다 다른 것은 전역 지침 파일의 위치와 주의사항뿐이라, 그 부분만 `tools/` 어댑터로 분리했다. 공통 원본에 도구별 사용법을 섞지 않는다.

**전역 연결은 "마커 블록 주입"을 택했다.** 전역 설정 파일을 심볼릭 링크로 덮거나 외부 스킬을 자동 설치하는 대신, 전역 파일의 관리 블록(마커 사이)만 생성·교체한다.

- 심볼릭 링크는 기존 전역 내용을 잃는다.
- 외부 스킬 자동 설치는 도구에 종속되고 원치 않는 것을 강제한다.
- 마커 블록 주입은 **기존 내용 보존 · 최초 백업 · 멱등 · 드리프트 점검**을 모두 만족한다.

**작업 기록은 캡처와 표현을 분리했다.** 기록 원본은 프론트매터가 붙은 마크다운 하나(집계·검색에 유리)로 남기고, 보기 좋은 결과물은 렌더링 층에서 만든다. 같은 원본을 Notion(집계·검토)과 HTML(시각화)이 공유하므로 중복이 아니다.

**외부 스킬·플러그인·오케스트레이션을 강제하지 않는다.** 반복 승인, 모든 작업의 티켓화, 리뷰마다 worktree 생성도 기본에 넣지 않는다. 같은 결과를 일반 문서와 절차만으로 만들 수 있어야 한다.

## 구성

| 위치 | 역할 |
| --- | --- |
| `AGENTS.md` | 모델·도구에 종속되지 않는 공통 핵심 규칙 |
| `workflows/plan.md` | 계획 수립 — 요구사항 구체화·이해 확인·스펙·작업 분해 |
| `workflows/implement.md` | 영향 조사·구현·검증 |
| `workflows/review.md` | 읽기 중심 코드 리뷰 |
| `workflows/handoff.md` | 맥락정리·인계 |
| `workflows/worklog.md` | 작업의 의사결정 서사 기록 |
| `guides/impact-scope.md` | 도메인·호환성·의존성 영향 조사 |
| `guides/design-discipline.md` | 모듈 책임·인터페이스·테스트 경계 |
| `guides/project-structure.md` | 프로젝트 문서 소유 위치와 권장 구조 |
| `tools/*/instructions.md` | 도구별 어댑터 (Codex, Claude Code) |
| `scripts/install.py` | 공통 원본을 전역 도구 설정에 연결 |
| `scripts/render_worklog.py` | worklog 마크다운을 HTML로 렌더링 |
| `worklog/example.md` | worklog 형식 예제 |

정보의 소유 위치는 이렇게 나뉜다.

| 정보 | 위치 |
| --- | --- |
| 개인 공통 규칙·작업 절차 | 이 저장소 → 전역 관리 블록 |
| 프로젝트 명령·규칙·도메인 지식 | 각 프로젝트의 `CLAUDE.md` / `AGENTS.md` |
| 모델·권한·훅·MCP 설정 | 도구별 설정 (이 저장소가 건드리지 않음) |

전역 규칙과 프로젝트 규칙은 도구가 자동으로 병합하고, 충돌 시 프로젝트 규칙을 우선한다. 프로젝트 문서 구성 권장안은 [guides/project-structure.md](guides/project-structure.md)를 따른다.

## 전역 연결

```sh
python3 scripts/install.py --dry-run   # 무엇이 바뀔지 먼저 확인
python3 scripts/install.py             # 실제 연결
```

- 현재 연결 대상: `~/.claude/CLAUDE.md`(Claude Code), `~/.codex/AGENTS.md`(Codex). 대상은 `scripts/install.py`의 `TARGETS`로 관리한다.
- 각 파일의 **관리 블록(마커 사이)만** 생성·교체한다. 마커 밖의 기존 내용은 그대로 둔다.
- 관리 블록이 없던 기존 파일은 최초 연결 시 타임스탬프 백업(`.bak-...`)을 만든다.
- 저장소 원본을 수정했거나 저장소 위치가 바뀌면 다시 실행해 동기화한다. 관리 블록에는 문서의 절대 경로가 포함된다.
- 연결 상태 점검은 `python3 scripts/install.py --check` — 원본 위치, 참조 문서 존재, 원본과의 동기화(드리프트)를 확인한다.
- 연결 해제는 `python3 scripts/install.py --uninstall`. 한 도구만 처리하려면 `--tool claude-code` 또는 `--tool codex`.

### 새 환경 세팅

새 개발 환경에서는 한 줄로 클론 → 연결 → 점검한다.

```sh
git clone git@github.com:llama-ste/agent-workflow.git ~/agent-workflow && cd ~/agent-workflow && python3 scripts/install.py && python3 scripts/install.py --check
```

설치 후 확인:

- `--check`가 모든 도구에 `✓ 정상`을 출력하는지 확인한다.
- 도구를 재시작하고 새 세션에서 전역 규칙이 실제로 로드되는지 확인한다(예: "지금 적용된 전역 지침을 요약해줘").
- 손으로 작성한 기존 전역 규칙이 있었다면 백업본(`.bak-...`)과 비교해 관리 블록과 중복되지 않게 정리한다.

### 다른 AI 도구 추가

도구마다 다른 것은 **전역 지침 파일의 위치**와 **도구별 주의사항**뿐이다. 새 도구를 연결하려면:

1. `tools/<도구>/instructions.md`에 도구별 어댑터를 추가한다. 공통 규칙과 다른 점, 그 도구의 제약만 짧게 적는다.
2. `scripts/install.py`의 `TARGETS`에 `"<도구>": Path.home() / "<전역 지침 파일 경로>"`를 추가한다.

`AGENTS.md` 규약을 읽는 도구는 Codex 연결 방식을, 별도 전역 지침 파일을 쓰는 도구는 Claude Code 방식을 참고한다.

## 작업 기록 (worklog)

각 작업의 의사결정 서사(배경 → 검토한 방향 → 트레이드오프와 결정 → 결과)를 프론트매터 마크다운으로 남긴다. 형식과 절차는 [workflows/worklog.md](workflows/worklog.md)를 따른다.

기록은 각 작업 저장소에서 생성하고, 개인 중앙 저장소(Notion 등)로 모아 성과 정리·회고에 쓴다. 공개 저장소에는 기록 데이터를 두지 않는다.

보기 좋은 결과물이 필요하면 렌더러로 HTML을 만든다.

```sh
python3 scripts/render_worklog.py 기록.md -o out.html --embed
```

프론트매터 → 헤더·배지, 서사 섹션 → 디자인된 페이지로 렌더링한다. `--embed`는 이미지를 data URI로 인라인해 단일 파일로 만든다(블로그·공유용). 예제는 [worklog/example.md](worklog/example.md).

## 검증

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

관리 블록 생성 내용, 문서 상호참조 무결성, 파일 병합·백업·제거의 멱등성, worklog 렌더링을 확인한다.
자동 검증은 스크립트 동작을 보장할 뿐, 모델이 실제로 지침을 따르는지는 판단하지 못한다. 새 규칙은 실제 도구 세션에서 관찰 가능한 동작으로 확인한다.

## 개발 노트

이 저장소를 수정할 때:

- **워크플로우·가이드 추가**: `workflows/` 또는 `guides/`에 `.md`를 추가하고, `AGENTS.md`의 "작업 절차" 목록에 한 줄 연결한다.
- **새 도구 연결**: `tools/<도구>/instructions.md` 어댑터를 추가하고 `scripts/install.py`의 `TARGETS`에 경로를 등록한다.
- **테스트**: `python3 -m unittest discover -s tests -p 'test_*.py'`
- **수정 반영**: 원본을 바꾸면 `python3 scripts/install.py`로 전역을 재동기화하고 `--check`로 점검한다.
- 전역 관리 블록(마커 사이)은 직접 편집하지 않는다. 항상 원본을 고치고 재실행한다.
