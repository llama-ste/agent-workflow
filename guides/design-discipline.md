# 설계 기준: 작은 인터페이스와 명확한 경계

새 모듈 설계, 공개 인터페이스 변경, 구조적 리팩토링 때 적용한다. 기존 코드를 이 기준에 맞추기 위해 작업 범위 밖으로 재작성하지 않는다.

## 깊은 모듈

- 작은 인터페이스 뒤에 의미 있는 동작과 복잡성을 감춘다. 호출자가 내부 처리 순서를 알아야만 사용할 수 있는지 점검한다.
- 모듈의 책임, 입력, 출력, 실패 조건과 부수효과를 설명할 수 있어야 한다.
- 내부 자료구조를 그대로 노출하거나 구현 단계마다 공개 메서드를 만들지 않는다.
- 인터페이스가 구현만큼 복잡하면 책임과 경계를 다시 검토한다. 작은 함수라는 이유만으로 새 계층을 만들지 않는다.

## 호출과 테스트의 경계

- 호출자와 테스트가 공유하는 동작의 경계(seam)를 명확히 한다. 기존 공개 경계를 먼저 활용한다.
- 가능한 한 적은 경계로 실제 동작을 검증한다. 테스트만을 위한 불필요한 공개 API를 추가하지 않는다.
- 테스트가 내부 호출 순서나 비공개 상태에 강하게 의존하면 관찰 가능한 결과로 바꿀 수 있는지 검토한다.
- 외부 서비스·시간·파일 접근처럼 제어해야 하는 의존성은 필요한 경계에서 분리하거나 주입한다. 모든 객체에 기계적으로 인터페이스를 만들지는 않는다.
- 추상화는 실제로 달라지는 구현·외부 의존성·정책을 다룰 때 도입한다. 미래의 가능성만으로 확장 계층을 만들지 않는다.

## 상태와 부수효과

- 계산과 외부 효과를 구분하고 가능한 계산은 값을 반환하도록 만든다.
- 공유 상태의 소유자, 갱신 순서, 실패 시 일관성을 분명히 한다.
- 트랜잭션·재시도·취소가 필요한 작업은 어디까지 원자적이며 중복 실행 시 어떻게 되는지 정의한다.
- 오류를 숨기거나 정상 값으로 바꾸지 않는다. 호출자가 처리할 실패 계약을 정한다.

## 설계 검토 결과

큰 변경은 책임·공개 계약·의존성·테스트 경계와 주요 대안의 트레이드오프를 남긴다.
기존 설계와 충돌하는 선택은 이유를 설명한다. 사전 리팩토링은 동작을 보존하는 별도 단계로 구분하고 관련 검증 전후 결과를 확인한다.
