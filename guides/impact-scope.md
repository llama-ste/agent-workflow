# 수정 전 영향 범위 조사

코드를 추가하거나 수정하기 전에 적용한다. 작은 수정은 관련 영역만 확인하고, 공유 모듈·계약·데이터 변경은 소비자까지 추적한다.

## 도메인과 기존 결정

- 프로젝트의 용어집, CONTEXT 문서, ADR과 설계 문서가 있으면 관련 부분을 읽는다.
- 같은 개념에 임의로 새 이름이나 동의어를 만들지 않는다. 코드와 문서의 용어가 다르면 차이를 확인한다.
- 새 도메인에서 용어가 불명확하면 주요 개념·관계·불변식을 먼저 정리한다. 반복해서 쓰일 지식은 기존 문서 위치에 남긴다.
- 기존 설계 결정을 바꿔야 한다면 이유, 영향, 대안을 설명한다. 단순한 버그 수정 때문에 용어집 전체를 만들지는 않는다.

## 기존 코드 변경

- 함수 시그니처·반환값·오류 형태를 바꿀 때 호출부와 테스트를 확인한다.
- 공유 타입·상수·유틸·설정을 바꿀 때 사용처와 기본값의 영향을 확인한다.
- 저장 형식·API·이벤트를 바꿀 때 기존 데이터와 구버전 소비자의 호환성을 확인한다.
- 간접 사용이나 외부 소비자를 확인할 수 없다면 조사 범위와 미확인 부분을 보고한다.
- 예상보다 범위가 커지면 요청에 필요한 변경과 별도 개선을 나눠 설명한다.

## 신규 구현과 기존 관례

- 도메인 용어와 동작을 기준으로 유사 기능을 검색한다. 재사용·확장·신규 구현 중 선택 이유를 밝힌다.
- 같은 계층의 명명, 의존성 방향, 오류 처리, 테스트 방식을 확인한다.
- 기존 패턴이라도 공식적으로 폐기되었거나 보안·정합성 문제가 확인되면 그대로 확대하지 않는다.
- 관례와 권장 방식의 차이는 적용 버전·근거·트레이드오프와 함께 보고한다. 단순한 유행이나 취향 차이를 문제로 만들지 않는다.
- 기존 코드의 정정 시점과 범위는 작업 목표에 맞춰 결정한다. 무관한 선례를 함께 수정하지 않는다.

## 의존성 추가

1. 표준 기능이나 기존 의존성으로 해결할 수 있는지 확인한다.
2. 새 의존성이 필요한 이유와 대안, 유지보수·라이선스·실행 환경·번들 또는 설치 크기 영향을 설명한다.
3. 사용자 요청에 이미 포함된 의존성이 아니라면 추가 전에 확인한다.
4. 추가 시 프로젝트 패키지 관리자와 잠금 파일 관례를 따른다. 전역 설치를 대안으로 임의 수행하지 않는다.

조사 결과는 관련 코드, 영향받는 소비자, 재사용할 구현, 미결정 사항 정도로 간결하게 정리한다.
